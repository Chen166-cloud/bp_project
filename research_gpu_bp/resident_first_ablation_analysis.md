# 第一组驻留消融实验独立分析

数据来源：`fast_bp/results/resident_20260917/ablation_small.json`；每配置5次预热、15轮随机交错计时。仅分析已有文件，未执行 GPU 工作。

## 结论

FP32 FFBP 的 Graph 与融合确实显示出较大的提速信号，但本轮并非稳定平台上的最终性能定论。GPU 监控中温度达到90°C，活跃状态频率多次低于2000 MHz；多个候选出现超过5%的前后半轮漂移，部分候选的 CV 超过20%。温度与频率变化是已观察事实，监控没有记录节流原因，也没有每次执行的墙钟时间戳，不能证明温度或功耗就是某次变慢的原因。

FP32 FFBP 的复误差仍约3.497%，FP64/mixed约3.286%；Graph的已保存质量指标与普通执行相同；融合在FP64/mixed下产生极小指标差异，尚未改变整体质量判断。它们解决执行成本，尚未解决达到1%复误差要求的问题。

## Graph 与融合的条件收益

下表的速度比是前配置中位数/后配置中位数；同时给出同轮比值的中位数和后配置胜出的轮数。每轮顺序随机，成对比值只能减弱慢漂移影响，不能消除轮内频率变化。

| 比较 | 中位数速度比 | 同轮比值中位数 | 后配置更快轮数 |
|---|---:|---:|---:|
| fp32: Graph / original | 1.642× | 1.783× | 15/15 |
| fp32: fusion / no Graph | 1.417× | 1.536× | 12/15 |
| fp32: fusion / Graph | 1.158× | 1.122× | 13/15 |
| fp32: Graph / fused | 1.342× | 1.342× | 15/15 |
| fp32: fusion + Graph | 1.901× | 1.957× | 15/15 |
| fp64: Graph / original | 1.053× | 1.016× | 11/15 |
| fp64: fusion / no Graph | 1.023× | 1.029× | 10/15 |
| fp64: fusion / Graph | 1.011× | 1.012× | 11/15 |
| fp64: Graph / fused | 1.040× | 1.024× | 10/15 |
| fp64: fusion + Graph | 1.064× | 1.033× | 13/15 |
| mixed: Graph / original | 1.024× | 1.021× | 11/15 |
| mixed: fusion / no Graph | 1.015× | 1.030× | 12/15 |
| mixed: fusion / Graph | 1.016× | 1.018× | 11/15 |
| mixed: Graph / fused | 1.025× | 1.013× | 12/15 |

| Direct FP32 Graph, chunk64 | 1.010× | 1.009× | 8/15 |

| Direct mixed -> phase32 + chunk256 + Graph | 1.781× | 1.810× | 15/15 |
| Direct mixed phase32 -> wrapped | 0.781× | 0.800× | 0/15 |

Graph在未融合和已融合程序上的效果应分开看；融合也分别在普通执行和Graph条件下比较。FP32原18.084 ms→原Graph11.015 ms→融合Graph9.513 ms，组合中位数速度比约1.90×；Graph条件下融合约1.16×。二者效果存在交互，不宜拆成固定可相加的时间收益。

FP64与mixed的小收益没有表现出同等稳健性。直接BP的FP32 Graph chunk64、256、1024分别约34.573、34.687、35.752 ms，现有波动不足以证明256优于64，或1024必然更差。

phase32探针相对原mixed同时改变chunk64→256并加入Graph；只能报告组合实现快约1.78×。应补原mixed、chunk256、Graph对照后，再解释三角函数精度的独立收益。wrapped对phase32保持chunk与Graph相同，当前数据表明其额外操作明显增加耗时，图像指标收益很小。

## 正确性与监控边界

FP32的original/original_graph/fused/fused_graph全部质量指标字段一致。FP64与mixed各自的普通执行和Graph指标一致，但融合相对原版的复误差分别变化−7.60×10⁻¹²、−4.91×10⁻¹¹，SER分别变化2.01×10⁻⁹、1.30×10⁻⁸ dB；属于极小但非零差异。这里仅有相对参考的汇总指标，未保存这些候选的完整复图，因此没有验证真实图像逐位一致。合成验证结论不能自动扩大到真实图。

监控共79条，P0且利用率≥90%的70条中，温度79–90°C；SM频率1620–2520 MHz，前后半中位数2505→2385 MHz；低于2000 MHz的活跃样本4个。监控覆盖初始化、预热、参考、测量和结果检查，不能精确定位到候选或计时轮。

后续应把短时精度核对与性能重复分开；重点配置做交错A/B复测，保存每次开始/结束时间戳与热状态。大规模FP64参考每ROI只需生成一次，不必混入所有性能轮长期加热GPU。新的计时不能与历史旧后端计时直接组成单因素加速比。

## 下一步最小 Nsight 采集

先用Systems采一个稳定后的完整resident帧，标注direct、leaf、regrid/merge范围，比较ordinary/Graph的CPU提交间隔、CUDA队列空隙、kernel累计时间与整帧时间。不要把系统时间线里的所有间隔都称作启动成本；需要同时看CPU API与GPU队列。[Nsight Systems用户指南](https://docs.nvidia.com/nsight-systems/UserGuide/index.html)。

Compute只选代表性的direct_chunk、leaf BP、低/中/高层regrid和fused merge实例。首轮使用`SpeedOfLight`、`LaunchStats`、`Occupancy`；只有出现计算或访存线索后，再分别增加`ComputeWorkloadAnalysis`或`MemoryWorkloadAnalysis`。关注实际DRAM读写量、L1/L2命中、寄存器/本地内存、执行管线利用率；调度器不能持续发射时再采`SchedulerStats`/`WarpStateStats`。指标名称随设备与版本查询，不先固定整套SASS计数器。[Nsight Compute官方Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)。

Profiler可能重放kernel、恢复内存并改变缓存和计时条件，因此采集用于解释机制，最终速度仍以独立、未插桩、同质量驻留测试为准。当前本机尚未发现Nsight工具，本文没有Nsight实测结论。
